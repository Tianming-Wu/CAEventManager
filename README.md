# CAEventManager

一场学生社团活动在现场要用到的东西：签到、任务进度、奖票发放、抽奖，以及每一次操作的留痕。自托管、
单进程，Python 3 标准库足够，没有第三方运行时依赖；前端是原生 JS，没有构建步骤。同一个进程服务主面板
（账号、活动列表、审批）与每个活动的 token 段（公示页、大屏、签到、控制台），新增活动不改变路径结构。

这份文件是一页纸的概览。**详细文档在 [`doc/`](doc/README.md)**：使用说明（`doc/usage/`）、
查得到的东西（`doc/reference/`：界面规范、术语、接口）、运维（`doc/ops/`）、设计与取舍
（`doc/design/`）。

## 路由

```
/                  主面板登录页（/login 是同一页）
/register          主面板注册（提交后待审核）
/panel             主面板控制台
/panel_static/*    主面板静态资源
/api/panel/*       主面板接口

/<token>/          活动公示页，只读，无鉴权
/<token>/screen    大屏投影页
/<token>/checkin   自助签到，须带 ?t= 时效 token
/<token>/admin     活动控制台，用主面板账号登录
/<token>/login     跳转到主面板登录，登录后回到该活动后台
/s/<code>          限时短码跳转，由控制台生成
```

活动后台没有自己的账号体系：它用主面板账号登录，沿用主面板的会话 cookie，因此同一个浏览器里
不需要输第二次密码。能否进入某个活动的后台，取决于该账号是不是这个活动的负责人或成员。

路由与外部前缀无关：路径里出现已知活动 token 时按活动处理，否则把剩余路径按主面板路由匹配，因此
本机直连、反向代理前缀、将来的子域名都无需改代码。`public_base_prefix` 只用于生成绝对链接
（二维码、分享链接、Cookie 路径），不参与路由判定。

活动有两个标识：数字 `seq` 只用于存储，不出现在 URL 里；`token` 是 32 位 base64url 的访问凭据，
本身就是 URL 中的一段。`path_secret` 是首个活动的 token，可在控制台重新生成，旧链接随即失效。

## 展示屏幕

大屏是一个可替换的插接件。活动默认使用自带的展示页（内置的 `classic`）；如需换成别的，
在活动配置里写入 `screen_pack: <标识>`，`/<token>/screen` 就改为提供那一份。

- 资源目录：实例目录 `screen_packs/<标识>/` → 内置 `builtin/screen_packs/<标识>/`
- 一份资源只需要 `screen.html`（以及它自己的 js/css），不需要 `module.json`，不声明能力
- 数据仍从 `/<token>/api/board` 与 `/api/stream` 取
- 「外部资源 › 展示屏幕」列出服务上有哪些可用、各自的标识与体积。**平台不设默认值**——
  活动不写就用自己的那份

站长与超级管理员可以在同一页**导入**一份屏幕：选一个 zip，服务端校验后落盘。导入前请确认
包内满足这些条件（页面上的「导入说明」也写着）：

- 有 `screen.html` 作为入口页；包内其它文件按 `screen/<文件名>` 相对引用
- 只接受 `.css` `.js` `.svg` `.png` `.jpg` `.jpeg` `.webp`；其余文件丢弃并回报
- 压缩包不超过 2 MB；解开后单文件不超过 2 MB、总量不超过 8 MB、最多 80 个文件
- 标识取自文件名（小写），重名时自动追加序号，不覆盖已有屏幕
- 白名单、体积上限等都是服务端的静态配置，见 `packs.py` 开头，改了重启生效

导入的屏幕与主站**同源**，因此只允许站长与超级管理员导入；删除后，仍引用该项的活动
会回到自带的展示页。上传部分不做解压到磁盘的动作：zip 逐个条目读进内存、校验条目名与
扩展名后才由服务端自己建目录写文件。

## 活动页面

公示页只读，展示签到人数、任务完成数、已发奖票与中奖名单。大屏页在签到阶段显示签到二维码，抽奖阶段
改为活动地址与常驻中奖名单。签到页必须扫大屏二维码进入：token 按 10 秒窗口切片，扫码通过后手机得到
签名 presence cookie，再填学号与姓名，两项都与名单匹配才算签到成功。

活动后台的页面栏由两方拼成：活动模块申请自己的页面（操作台、名单、奖票、抽奖、奖票设置），平台
追加「活动设置」与「日志」。活动设置是平台画的，管的是与玩法无关的东西——成员、活动本身的信息。

## 名单

平台里除了活动，还存着一批批**名单**：社团成员、某次比赛选手这类可以反复用的名单。名单与活动并列，
不挂在某场活动下面，活动从名单里取人。

- 「名单与报名 › 我的名单」里新建、导入、打开与设置
- 导入支持 CSV / TSV，第一行可以是表头（学号、姓名、班级、分组、备注），没有表头时按「学号,姓名,班级」
  读取；按学号增量合并：没有的人新增、已有的人更新资料，导入后报告新增几人、名单内已有几人、
  有几行读不了
- 成员可以标成「已退出」而不删（历史留着），也可以直接移出
- 导出为 CSV（带 BOM，Excel 直接打开）；交人用的表格与报名表随后补上
- 人是平台级的：同一个人在多份名单里是同一条人员记录，改一次姓名各处一致

可见性三档：**私有**（只有创建者）、**公开**（所有登录账号可看）、**组织公开**（组织建立前等同公开）。
看得见不等于改得动，写权限是单独一件事：

- 公开的名单上，谁都能点「申请写入权限」。申请后是**立刻生效**还是**等拥有者确认**，由这份名单自己的
  设置决定（默认立刻生效——现场多人帮忙时不该等人）
- 私有的名单没有申请入口，只能由拥有者按登录名邀请
- 拥有者永远可写、也可以随时把人移出；被授予的人改不了"谁能写"这件事，也不能删名单
- 站长与超级管理员在「全部名单」里能看到服务上所有名单，但**不能**借此获得写权限

人是平台级的：同一个人在多份名单里是同一条人员记录，改一次姓名各处一致。院系与班级分开两列。

## 报名

报名是一个公开链接，报名成功的人直接写进某份名单——名单自己「长出来」的那条路。

- 「名单与报名 › 我的报名」里创建：名称、说明、**写入哪份名单**、可选的**限制范围**
- 限制范围默认关闭：任何拿到链接的人都能报名。开启后只有所选名单内的成员可以报名，学号与姓名
  都要与名单记录一致（与签到页同一套校验）
- **时间**与**名额**各由一张卡片上的开关决定是否启用。启用时间时开始与结束都可留空：留空表示那一端
  没有边界（不设下界／不设上界），两端都填时开始必须早于结束。名额启用后填上限，满了自动停收
- **重复提交**按学号判断，分三种情况：信息与上次完全一致时提示「您已经报过名」并不做任何事；
  信息不一致时，取决于「报名后修改」这一项——不允许则提示联系负责人，允许则问「您希望更新信息吗」，
  确认后才覆盖原记录
- **收集字段**：学号与姓名固定必填；院系与班级各由一个复选框决定收不收；其余字段自己加，类型有
  单行文本、多行文本、数字、单选、日期，可以标必填。每个字段选一个去向：只留在本次报名、写入院系、
  写入班级、写成名单里的分组、写成名单里的备注。选了去向的字段会直接落到人员库或名单条目上
- **视觉效果**：主题四档（素色／暖色／冷色／暗色）加一个主色，管理页右侧即时预览；报名页只换这几个值，
  页面结构不变
- 公开页地址是 `/join/<报名 token>`，不需要登录；提交记录在报名详情里查，也能导出成 CSV

## 账号与权限

账号分三级：站长（唯一）> 超级管理员 > 管理员。注册一律先落到「管理员 + 待审核」，审核通过才能登录。
用户管理、活动管理、审批只对超级管理员及以上可见，服务器管理与审计日志只对站长可见，接口层同样校验。

敏感操作分两层：轮换活动访问地址、存档活动、封禁或停用账号、修改角色需要重新输入一次密码，进入 sudo
模式后十分钟内不再询问；其余操作（审核、启用、重命名、邀请）只做一次弹窗确认。sudo 模式记在会话上，
同一账号在另一台设备登录不会继承，退出登录或切换账号立即失效。活动后台的「解锁修改」是另一回事，
它管的是现场操作台里的撤销、改时间、删人与重置奖票，30 秒无操作自动上锁。

### 成员

活动后台用主面板账号登录，但能不能进取决于是不是这个活动的成员。负责人在活动后台的「活动设置」
里邀请：按登录名或称呼搜到人、发出邀请，对方在自己的面板「我的活动」里确认一次才算加入。

移出成员不删记录：席位变成「已移出」并留下时间，名单里灰显保留，随时可以重新邀请——重新邀请
同样要对方再确认一次。负责人不能把自己移出，也不能移出活动里唯一的负责人。

### 登录名

`[0-9A-Za-z_-]`，3~24 位——中文、空格、点号都不收（这些字符在 URL、脚本、日志里都容易出岔子）。
`admin`、`root`、`owner`、`support` 这类看着像官方的词属于保留词，注册与改名都用不了。

登录名不分大小写地唯一。**「被占用」与「被保留」对外是同一句话**（「这个登录名不可用」），
状态码也一样：注册口不该变成"哪些名字存在"的探针。同一来源十分钟内连着试到 8 次就先歇一会。

### API 令牌

给平台之外的程序用：脚本、群机器人、别的 Agent。入口在「账户信息 › API 令牌」，一人一张或多张。

- 形如 `cae-` + 43 位随机字符；**在浏览器里生成**：只有它的 sha256 与前四位、后五位会发到服务端，
  明文既没经过网络也没进过服务端的内存。之后任何地方都只显示 `cae-abcd•••••wxyz9` 这种首尾几位
  （服务端只留哈希与前四位、后五位，明文不落库）
- 用法：`Authorization: Bearer cae-…`。带令牌的请求不必带 `X-Requested-With` 标记——
  那是为"浏览器会自动携带的 cookie"设的防线，令牌没有这个问题
- 三档范围：**读取**（列表、详情、导出）、**写入**（名单、报名、活动设置的日常改动）、
  **平台管理**（账号、活动生命周期、外部资源）。账号本身的权限仍然生效，令牌只能在其下再收窄
- 令牌**做不到**这四件事：**发新令牌 / 吊销令牌**、**改账号自己的信息**（显示名、登录名、头像、
  密码）、**需要重新输密码的动作**（sudo 提权靠人再输一次密码，令牌背后没有人可问）、
  以及**超出它自己范围**的操作。超管或站长的令牌仍能操作用户列表——那是账号权限，不是令牌权限
- 有效期可选「永不过期 / 30 天 / 90 天 / 一年」，随时可以吊销，吊销即刻失效
- 审计里操作人仍然记本人，detail 后面带一句 `令牌「群机器人」`——事后分得清是人点的还是程序调的
- 浏览器拿不到 WebCrypto 时（比如从局域网用 http 打开）会退回服务端生成，界面会说明这一次是
  服务端生成的

## 运维助手

「总览」下面的**运维助手**把"查一下"变成一次对话：某场活动为什么没人报名、名单里有没有这个人、
最近谁改过东西。它不会绕过权限——**助手用的就是当前账号的会话**，所以它能看到、能做的，与本人手点
出来完全一致。

- 模型**每人一份**：接口地址与模型名有默认值（`https://api.deepseek.com` / `deepseek-flash`），
  所以通常只需要填一把密钥；「获取模型」会问一次服务端的 `/models`，把可选模型名列出来
- 密钥**只写不读**：保存后输入框里放一串星号（假内容，不是真密钥），再保存不会被清掉；
  要换就直接覆盖，要删就点「清除密钥」。接口永远不回传密钥
- 一次对话最多来回六步工具调用；过程里调了什么会以小标签显示在回答上方
- 目前开放的都是**只读**工具：活动列表与公示数据、名单与成员、报名与提交记录、人员检索、
  审计日志（超管及以上）、服务器状态（仅站长）
- **改数据的动作一律不开放**，助手会告诉你去哪个页面操作。放行与否只走 `policy.verdict()`
  一个口子，以后接自动审计引擎时换的只是它
- 问一句**不进审计**：审计只记真正的操作。将来助手能改数据时，那次写入自己会记一条，
  detail 里带「经助手」
- 没配密钥的账号看到的是「还没有密钥」，点配置按钮填一把即可（地址与模型有默认值）；
  填之前不会发出任何请求

### 对话存档

- 对话按**会话**存下来，下次回来接着聊；输入框上方那条就是当前会话的名字，点开是会话列表
  （左侧抽屉），可以改名、删除、导出 Markdown
- 会话 id 在地址里（`.../panel#/assistant/<id>`）：开几个标签页就是几段互不打扰的对话
- 每个账号有一份**存档配额**（按字节算，默认 512 KB）。满了不会再存新的，页面会提示清理；
  真的不够用的人由站长在「用户管理」里单独调——那里也能看到某人已经存了多少
- 存档的内容只有对话本身（角色、文本、用过的工具名），不含模型密钥
- 新会话存下之后会请模型起一个短名字（不超过 12 个字）；起不出来就留着第一句话

### 平台提示词

平台自己的规矩（称呼、语气、本社团的固定说法）可以单独写在一份 markdown 里，手工维护：

```
<数据目录>/assistant_prompt.md          # 例如 ~/apps/lottery/data/assistant_prompt.md
```

- 内容是**追加**在固定规则（只回答平台范围内的事、照实说无权、不编造、用简体中文书面语）
  之后发出去的，不用重抄这些规则；文件不在、空着、读不动，就当没有
- 按修改时间缓存：改完存盘，**下一句话**就带上新内容，不用重启服务
- 上限 20 KB，多出来的部分截掉
- 想放到别处可以用环境变量 `LOTTERY_ASSISTANT_PROMPT` 指一个绝对路径（测试与特殊部署用）

里面可以写变量，发出去之前按**当前这次对话的人**换成具体值：

| 写法 | 换成 |
| --- | --- |
| `${user.username}` | 登录名 |
| `${user.name}` | 称呼（没填就是登录名） |
| `${user.role}` | 身份：站长 / 超级管理员 / 管理员 |
| `${user.roleKey}` | `owner` / `superadmin` / `admin`（想按身份分头交代时用） |
| `${user.id}` | 账号 id |
| `${panel.name}` | CAEventManager |
| `${panel.version}` | 版本号，如 `1.7.0.20` |
| `${tools}` | 这个账号能用的工具名，顿号隔开 |
| `${time.date}` | 2026-11-07 |
| `${time.time}` | 20:42 |
| `${time.now}` | 2026-11-07 20:42 |

没写到的占位符**原样留着**（写错能一眼看见，不会悄悄变成空白）。变量只在这份文件里生效，
不会出现在聊天记录或审计里。

### 助手看得到什么

一次对话发给模型的只有三样东西：**系统提示**（固定规则 + 「当前使用者：站长（owner）。」+ 上面那份
平台提示词）、**这个账号能用的工具清单**、**这段对话本身**。没有别的东西被塞进去。

- 它**不直接读数据库**：每个工具都是以这个账号的会话，调用平台自己的接口（`127.0.0.1` + 本人的
  cookie + `X-Via`），所以权限、CSRF、冲突、审计一处都没绕开——它能看到的，就是这个人手点能看到的
- 「是不是站长」靠两件事：系统提示里写明的身份，以及**工具清单本身就按角色收窄**
  （`policy.visible`）。普通管理员的请求里根本没有 `host_stats`、`recent_audit` 这两个工具，
  模型连"有这回事"都不知道，也就不会去试
- 九个工具都是只读：活动与公示数据、名单与成员、报名与提交、人员检索、审计日志（超管及以上）、
  服务器状态（仅站长）
- 工具结果里有平台上的姓名、学号等内容，它们会随对话发到**你自己配的那个模型端点**——这就是为什么
  密钥与端点归每个人自己
- 聊天记录存在平台数据库里（每人有配额），密钥永远不进对话

## 多会话同步

同一份数据可能同时开着好几个会话：两个管理员、同一人的两台设备，或者现场多位工作人员各自用手机
打开活动后台登记。一处改动会在片刻之内出现在别处，不需要手动刷新。

活动后台是主要的多人场景，对象因此划分得很细——**一个学生就是一个对象**。两位工作人员登记两位
不同的学生互不影响；同一个人被两个人登记时，只要结果相同就算同一件事，不报错。总面板的写法相同，
对象是账号、活动、预设。


- 服务端在每次成功的写入之后把相关对象的版本号加一；两处都通过服务端事件流推送
  （总面板 `GET /api/panel/stream`，活动后台 `/<token>/api/admin/stream`），客户端收到后
  重新读取当前页面；活动后台的 5 秒轮询保留为事件流连不上时的兜底；
- 版本号按对象记（`account:7`、`event:3`、`preset:x.y`），不是整块面板一个号。两个会话改的
  不是同一个对象时，各自成功，互不影响；
- 每个写入请求带上客户端各对象的版本号（`X-Rev-Map`）。只有**同一个对象**被别人先改过、
  且本次要落地的状态与当前状态不同时才算冲突：服务端拒绝（409），界面在右上角提示，并以
  服务端状态为准——先到的写入生效；
- 想要的状态已经是事实时不算冲突：两人先后把同一账号设为同一状态，第二个不报错，服务端保留
  第一个人的时间与操作人。

连接断开不会造成数据不一致：重连后收到的是完整版本号，落后的会话会一次性对齐。

大屏与公示页走同一条事件流（`/<token>/api/stream`，不需要登录），只收本活动的变化，别的活动
的写入会被丢掉。事件流连不上时它们照旧轮询（大屏 1.5 秒、公示 5 秒）；连上之后轮询降为半分钟
一次的对账读取，用来兜住偶发漏收。公示页的读取带 `ETag`，没有变化时服务端回 304、不再重发名单。

### 重新部署之后

服务重启不会把任何人踢下线，但**已经开着的页面跑的还是旧脚本**。所以每个回答都带着版本号
（`version` 字段，事件流帧里也有）：

- 页面第一次收到只记下来，之后版本号变了就算「服务换过版本了」；
- 面板：这一页没敲过字、没有开着的弹窗，就**直接刷新**；否则在内容上方出一条
  「服务已更新到 vX，刷新后使用新版本」，点「刷新」再换。填了一半的表单不会被吞掉；
- 大屏：抽奖动画正在播时先记着，放完再刷新——现场不会看到一半的动画被切断；
- 公示页没有要保住的东西，直接换成新的。

版本号同时是认出"这是哪一次部署"的凭据，所以**每次上线都要推进**（见下一节）。

## 长列表

可能很长的列表一律分页读取、并且搜索在服务端完成：账号、审计日志、归档活动都是「一次取一页，
按需再取」，页头显示总数。活动自己的名单、奖票、抽奖记录不分页——现场需要一眼看全。

## 奖票池

| 模式 | 取值 | 说明 |
|---|---|---|
| 自动 | `到场人数 × 3 + 常数`（常数默认 20） | 跟着真实到场人数走，保底票永远发得出 |
| 固定 | 指定张数 | 印了确定数量实物票时使用 |
| 表达式 | 例如 `signed_in * 3 + 20` | 每次状态变化重新求值，按现场形状伸缩 |

每张票按顺序发号，与池子大小解耦，因此池子可以中途上调，也可以下调到不低于已发张数。表达式由小型
AST 求值器执行，只允许数字、上下文名字、四则运算与 `min` `max` `round` `abs` `int`，没有 `eval`；
可用名字有 `signed_in`、`present`、`participants`、`staff_present`、`tasks_done`、`guaranteed`、
`bonus_constant`、`pool_size`。

## 任务链

参与者依次完成签到 → 任务一 → 任务二，前一环没有完成时后面的标记会被拒绝，并指出缺哪一步。

现场总会有例外（设备故障、临时改流程）。打开操作台右上角的「解锁修改」之后，管理员可以越序标记，
这一条会在操作日志里带上「越序：未完成 ……」的说明，导出包里的操作日志同样保留——数据上留下的
是"当时确实这样做了"，而不是把它抹平。

## 抽奖去重

两个独立开关，在活动后台的「奖票设置」里：

- **同一个奖不重复同一个人**：一个奖有几个名额，同一个人只会在其中一份里出现。
- **一个人不能同时拿两个奖**：中过任何一个按票抽取的奖之后，此人的票不再进入其它奖项的抽取。

按人抽取的奖（例如特等奖，所有到场者等概率）只受第一条约束：它本来就不是"抽票"，与按票的奖项
互不排斥，中过按票的奖的人也仍可被抽中，反之亦然。

作废一条抽奖记录，该人即恢复资格。

## 抽奖节奏

每个奖品在后台「抽奖」一栏里各有一档「逐个 / 一次抽完」，随奖品一起保存，换台电脑打开也是这一档：

- **逐个**：点一次抽出一个人，配合大屏动画，适合名额少、要仪式感的奖。
- **一次抽完**：点一次抽出该奖品的全部剩余名额，适合名额多的小奖，省时间。

一次抽完仍然是一张票一张票地消耗，作废规则与两个去重开关都不变；大屏收到整批结果后只播一次动画，
再把这一批的得主一次列出来。材料不够时（例如可抽的票少于剩余名额）会抽出能抽的部分并说明原因。

## 名单与导出

名单支持 CSV 与 TSV 导入，有表头自动识别，无表头按「学号,姓名」解析，按学号增量更新，重复导入不留
重复记录。姓名拼音由内置拼音表生成，检索同时匹配姓名、全拼、首字母与学号片段。所有动作写入审计日志；
活动结束后从名单页导出 ZIP：`01-汇总`、`02-名单`、`03-奖票明细`、`04-抽奖记录`、`05-中奖汇总`
五张 CSV 与 `06-操作日志.log`。

## 归档

活动不会消失：存档之后它从列表里退到「活动管理 › 归档的活动」，标题、负责人、归档时间都留着，
数据库文件不动。归档是带 sudo 的操作，所以那边不再给"取消归档"按钮——要做也是另一次显式操作。

归档列表是分页的（一次 20 条，按需再取），不会把历年的活动一次全读出来。

## 活动模块与预设

`modules/<id>/` 下放 `module.json`（标识、名称、版本、兼容约束、页面清单）与 `schema.json`（创建时定下的
参数）。创建活动的表单由 schema 生成，取值校验通过后写进该活动自己的库；兼容约束按本版本号判定，不满足
的模块不出现在创建列表里。`templates/<id>.json` 是模块之上的一种安排：选定模块并预填参数或默认活动名，
只能设置模块已声明的参数，写别的键会被拒绝。

### 模块与预设的关系

模块是**能力边界**：装上并启用某个模块，才有它允许的那些设置与页面；停用之后引用仍然保留，只是不能再
拿它开新活动（已开的活动不受影响，成员、成绩这些照旧可读）。

预设是**边界之内的一个练好的配置**：模块的参数很多，一项项调到想要的效果要费工夫，预设把其中一种调好
的结果存下来，下次换名称和人数就能开。所以预设一定依赖某个模块，也可以依赖另一个预设（在它的基础上改）。

```
builtin/modules/<模块>/module.json     模块本体
builtin/modules/<模块>/templates/*.json  随模块发布的预设
builtin/templates/*.json               随版本发布的预设
modules/, templates/                   本实例自己装的，不进版本库
```

预设文件里的依赖写成：

```json
"dependency": { "module": "nwuca.lottery", "template": "nwuca.lottery.salon" }
```

导入一个预设时，如果它依赖的模块不存在（或被停用），会先说清楚，再由人决定是否仍然导入；导入之后它
照常列出，只是标为不可用。

### 预设

预设是一份**存下来的活动配置**：用哪个模块、那套参数、以及建议的活动名称。它不是"可配置项清单"，
而是某个活动当时的设定快照——在活动卡片菜单里「保存为预设」，下次建活动时挑一份，改改名称和人数
就能开下一场。

预设分三处：我收藏的、我创建的、预设广场。可见性三档：私有（只有自己）、公开（广场里所有人）、
组织公开（组织建好之后只对本组织可见，目前按公开处理）。内置预设来自 `templates/*.json`，启动时
同步进数据库，所以列表只有一个来源。

## 部署

目标是一台能 ssh 的 Linux 主机，只需要 python3 与 tar。

```powershell
.\deploy.ps1 -Remote user@host              # 上传并重启
.\deploy.ps1 -Remote user@host -NoRestart   # 只同步，远端目录默认 ~/apps/eventmanager
```

脚本归一化行尾后打包源码，用 `cmd /c type` 把 tarball 原样经 ssh stdin 送出（目标机没有 sftp），
远端解包，逐个确认文件落地并试 import 主模块，全部通过才重启；远端的 `data/` 与 `config.json` 始终不动。

### 版本号

版本号写成四段 `主.次.修.构`，在 `app.py` 的 `VERSION`：

| 段 | 什么时候动 |
|---|---|
| 主 | 架构或兼容性变了（老模块、老预设、老数据库要跟着动） |
| 次 | 一批新功能落地 |
| 修 | 行为变化，或一批修复 |
| 构 | **只增不减**：推进任何一段它都跟着 +1，永不清零。所以它是"这台机器的第几次发布"，可以当唯一的部署序号用（大致等于提交数，但不依赖版本控制系统去读） |

**每次提交并上线都要推进，至少推进「构」**：

```powershell
python tools/bump_version.py            # 只推进「构」
python tools/bump_version.py patch      # 「修」+1，「构」也 +1
python tools/bump_version.py --show
```

页面开着的时候服务换了版本，会按上一节的方式自己刷新或给出提示——这依赖版本号真的在变，
所以这不是形式主义。

```sh
cd ~/apps/eventmanager
./service.sh status            # 打印公示 / 大屏 / 控制台三个地址，活动前先跑一次
./service.sh start|stop|restart
./service.sh log 50            # 另有 check / reset
```

服务日志是 `data/service.log`（`run.sh` 把 stdout 追加进去）。它自己轮转：写到 8 MB 时改名为
`service.log.1`，旧的依次往后挪，最多留三份（`.1` ~ `.3`）；`LOTTERY_LOG_MAX=0` 关掉轮转，
也可以给一个别的字节数。日志写不出去不会让请求失败。

服务不会自动拉起。挂载在 `https://example.org/mount` 时，活动页形如 `https://example.org/mount/<token>/`，
大屏、签到、控制台是同前缀下的 `screen`、`checkin`、`admin`。部署后可用 `tools/` 下的脚本自检：`unit_test.py`
无需服务，`panel_test.py` 打主面板接口，`smoke_test.py` 打活动接口，`panel_ui_test.py` 与 `ui_test.py`
用 Playwright 驱动真实页面。

## 配置

`config.json` 位于仓库根目录，首次启动时自动写入。

| 键 | 默认值 | 作用 |
|---|---|---|
| `path_secret` | 自动生成 | 首个活动的访问 token，也是它的 URL 段 |
| `host` | `0.0.0.0` | 监听地址 |
| `port` | `8931` | 监听端口 |
| `public_base_prefix` | `http://127.0.0.1:8931` | 对外访问前缀，只用于拼绝对链接 |
| `owner_username` | `owner` | 站长登录名 |
| `owner_name` | `站长` | 站长显示名，界面只出现这个 |

活动标题、奖票池、奖品、大屏阶段、导出时区等属于单个活动，存在该活动自己的库里，不进 `config.json`。
环境变量可覆盖：`LOTTERY_CONFIG`、`LOTTERY_DATA_DIR`、`LOTTERY_HOST`、`LOTTERY_PORT`、
`LOTTERY_PACKS_DIR`（导入的屏幕放哪）、`LOTTERY_VERSION`（仅测试与预发：起两个版本号不同的实例，
验证页面的热更新）。数据目录中，
`data/panel.sqlite3` 存账号与活动元数据，`data/events/<seq>.sqlite3` 是每个活动自己的库，`data/avatars/`
存头像，首次启动生成的站长密码在 `data/owner_password.txt`。
